## Context

本次变更源于一次以 Chrome DevTools MCP 为工具的全量前端性能测量（7 视图 / 8 停靠栏 / 弹窗 / 图表交互 / 滚动）。测量同时产出了**结论**与**被证伪的假设**，两者都必须被固化，否则下次会被重新讨论。

关键背景约束：

1. **上一次性能修复是靠肉眼发现的**：ScreenerView 挂载 3,847 行导致 46,487 DOM / 首屏 4,838 ms / 帧 548 ms。没有门禁，它是被"点导航栏超时 4 秒"这个现象偶然暴露的。
2. **已有的诚实教训**：先前一轮曾把 400–700 ms 帧耗时判为"加载中假象"并排除——该判断本身正确，但**当时后端已挂**，热路径根本没跑，导致真实成本被掩盖。故本设计把"测量前置条件校验"提升为硬要求。
3. **测量工具的能力边界**：纯 JS 主线程 CPU 成本（bundle 解析执行、对象拷贝）与内存行为，在 Playwright 中不可见；必须用真实 trace 与堆采样。

## Goals / Non-Goals

**Goals**

- 让"前端变慢了"成为一个**能被自动拦下的事件**，而不是某天被用户感知。
- 建立**节流档位下的真实基线**，使预算有物理意义。
- 消除已确认的首屏瓶颈（单块 JS、字体阻塞 CSS）。
- 固化已证伪的假设，降低重复调查成本。

**Non-Goals**

- 不追求 Lighthouse 满分。测量目标是**交互式终端的真实响应**，而非综合评分。
- 不优化本地未节流的 409 ms LCP —— 该数字缺乏物理意义。
- 不为 `klinecharts` 内部的强制回流做改造（上游第三方，实测收益为零）。
- 不在本变更内引入 RUM / 真实用户监控（属后端或运维范畴，另议）。

## Decisions

### D1: 以 Chrome DevTools MCP 为基准工具，Playwright 退为交互驱动

**决策**：性能测量以 DevTools MCP 的 `performance_start_trace` / `performance_analyze_insight` / `emulate` / `take_heapsnapshot` 为准；Playwright 仅用于需要脚本化交互或 E2E 断言的场景。

**理由**：Playwright 只能测得"我手写出来的指标"（DOM 数、rAF 间隔）。本次测量中，**bundle 体积驱动的 render delay（2,163 ms）与强制回流归因（klinecharts, 31 ms）恰恰是 Playwright 永远看不到的**。若沿用 Playwright，将继续停留在 DOM 计数这一层。

**代价**：Chrome DevTools MCP 依赖单一 Chrome profile，曾被 profile 锁阻塞；且其网络面板不透出 WebSocket 连接。**缓解**：profile 锁以独立 `--isolated` 实例规避；WS 连接数以 `initScript` 注入 WebSocket 钩子计数（本方法已在本次测量中验证可用）。

### D2: 预算以「节流档位」为基准，未节流数字只作对照

**决策**：正式基线固定为 **4× CPU 降速 + Fast 4G**；同时记录未节流（1× / 无网络限制）数字，但后者 MUST 标注为对照值，不得作为预算依据。

**理由**：未节流下 LCP 409 ms、TTFB 4 ms（本地服务）会给出"性能极好"的错误安全感；节流后 LCP 2,178 ms 才暴露 87% 预算消耗。阈值判断必须发生在与真实设备可比的条件下。

**代价**：节流档位是模拟值，不等于任意真实设备。**接受**：目标是"可复现的相对基线 + 回归检测"，而非绝对真值。

### D3: 预算采用「实测基线向下取整」，与现有覆盖率棘轮策略一致

**决策**：所有预算值 MUST 取自实施时的实测基线并向宽松方向取整，MUST NOT 采用未经验证的猜测值；确立后**只升不降**（越严越难放宽）。

**理由**：与 `ci-quality-gates` 已确立的覆盖率棘轮哲学完全一致（"阈值不高于基线""基于实测向下取整"）。复用同一哲学避免仓库内出现两套互相矛盾的阈值制定逻辑。

### D4: 首屏 JS 以「视图边界 + 重型库边界」双维度拆分

**决策**：按视图（`React.lazy`）拆分，并把 `klinecharts` / `klinecharts-pro` / `recharts` 等重型库移出初始块；初始块体积设上限并入门禁。

**理由**：当前是单块 975 KB，且**全仓库零动态 import**（唯一一处 `import()` 在测试文件里）。用户打开图表视图却要下载并解析全部 7 个视图与全部图表/图表库。render delay 占 LCP 的 99%，说明收益集中在主线程工作量上。

**代价**：引入视图切换时的加载态与潜在的加载抖动（CLS 风险）。**缓解**：拆分后 MUST 复测 CLS，并以骨架屏占位避免位移——`frontend` 已有 Skeleton 原语可复用。

### D5: 「已证伪假设」作为一等产物记录

**决策**：把本次被证伪的优化假设（`localeCompare` 排序占 0.63%、强制回流收益为零）写入规格的**非目标**或测量文档，而非仅留在对话里。

**理由**：`localeCompare` 是一个极容易被反复"优化"的目标（看起来昂贵、替换极简单）。若无记录，下一次性能调查会再花一轮测量把它重新证伪。**记录证伪结论与记录结论同等重要。**

### D6: 粘性 DOM 先定性、后修复，不预设它是泄漏

**决策**：对"浏览后 DOM 从 701 涨到 1,072 且不回落"先做归因（缓存设计 vs 卸载遗漏），再决定修复方式；本变更只要求**给出结论并固化相应断言**。

**理由**：堆内存实测为**锯齿形**（18.3 → 30.9 → 36.6 → **11.2** → … → 42.6 MB），GC 明确在回收，**没有泄漏证据**。DOM 单调上升后**收敛于 1,072**（有界）。贸然按"内存泄漏"修复会打错靶子；但无界增长与有界粘滞必须被区分，故需断言。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|---|---|---|
| CI 运行真实浏览器成本高、易 flaky | 门禁被绕过或频繁误报 | 性能门禁独立 job；预算取宽松侧；如浏览器不可得，退化为"体积 + 静态预算"子集并**显式记录降级** |
| 节流测量耗时（单次 trace 数十秒 × 多视图） | CI 时长膨胀 | 全景测量保留为**人工/定期**；CI 只跑首屏关键路径子集 |
| 视图拆分引入 CLS 回归 | 首屏稳定性变差 | 拆分 MUST 伴随 Skeleton 占位并复测 CLS |
| 预算过紧导致正常迭代被阻塞 | 团队绕过门禁 | 棘轮策略 + 实测基线取整；预算变更需在 PR 中说明理由 |
| 合成点击导致 CLS 读数失真 | 预算基于错误数字 | CLS 预算 MUST 基于**真实（可信）输入**复测后确定 |

## Migration Plan

1. 先落地**测量规程与基线**（不改变产品行为），产出基线表。
2. 再落地**体积/拆分改造**（改变构建产物），复测并确立预算。
3. 最后**接入 CI 门禁**——必须在基线存在后才启用，否则门禁会以错误阈值上线。
4. 回滚：拆分改造为独立提交，可单独 revert；门禁为独立 job，可单独禁用而不影响既有门禁。
