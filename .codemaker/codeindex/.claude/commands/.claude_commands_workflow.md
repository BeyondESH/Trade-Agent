## 业务意图（这个子模块解决什么问题）

本仓库全部功能需求都以 OpenSpec change 形式立项（`openspec/changes/` 现有 81 份已归档 change、`openspec/specs/` 131 个 capability）。推进组四条命令解决的是同一个问题：**让 Agent 在正确的时刻做正确的那一个动作**——想清楚（explore）、说清楚（propose）、实现（apply）、收口（archive），并且每一步的状态判定都交给 `openspec` CLI 而不是模型记忆，避免"还没立项就开始改代码"或"任务没做完就归档"。

四条命令不是强制顺序的阶段机，而是"actions on a change"模型：`apply.md` 明确写了 **Can be invoked anytime**，允许在工件未齐、部分实现、与其他动作交错时调用；`explore.md` 更声明自己是"**a stance, not a workflow**"（没有固定步骤、没有必需产物）。

## 对外接口

| 命令 | 方向 | 关键入参 | 业务说明 | 入口文件 |
|------|------|---------|---------|---------|
| `/opsx:explore` | 人 → Agent | 任意话题 / change 名 / 什么都不给 | 思考态：只读代码、可以创建规划工件，**绝不写实现代码** | `opsx/explore.md` |
| `/opsx:propose` | 人 → Agent | kebab-case change 名 **或** 一句需求描述 | 建 change 并一次性补齐 `applyRequires` 里的全部工件 | `opsx/propose.md` |
| `/opsx:apply` | 人 → Agent | change 名（可省，模糊时必须弹框） | 按 `tasks.md` 循环实现，完成即勾选，阻塞即暂停 | `opsx/apply.md` |
| `/opsx:archive` | 人 → Agent | change 名（可省，模糊时必须弹框） | 完成度校验 → 可选 sync → `mv` 到 `changes/archive/YYYY-MM-DD-<name>` | `opsx/archive.md` |

> 方向说明：这些命令没有网络协议对端，"人 → Agent"即人输入斜杠命令、Agent 通过 Bash 只读/写 `openspec` CLI。`allowed-tools: Bash(openspec:*)` 是唯一的工具授权声明（来源: `.claude/commands/opsx/*.md` frontmatter）。

## 实现约束清单

> 修改或新增推进组命令前，逐条核对；每条都是"违反即静默出错"的类型。

### 必须定义的常量/枚举

| 标识符 | 值 | 所在文件 | 说明 | 约束由来 |
|-------|----|---------|------|---------|
| `SCHEMA_DEFAULT` | `spec-driven` | `openspec/config.yaml` | 本仓库唯一启用的 schema；工件 id 为 proposal / specs / design / tasks | 仓库未启用自定义 schema；实现自定义 schema 后命令文本必须仍不硬编码工件名（来源: `.claude/commands/opsx/update.md`） |
| `APPLY_STATE_BLOCKED` | `blocked` | `opsx/apply.md` | 工件缺失态 → 不得开始实现，只能提示 `/opsx:continue` | 缺工件即写代码会造成实现早于需求（来源: `.claude/commands/opsx/apply.md`） |
| `APPLY_STATE_ALL_DONE` | `all_done` | `opsx/apply.md` | 全任务完成态 → 输出祝贺并建议 archive，不得自动归档 | 归档需人确认完成度警告（来源: `.claude/commands/opsx/archive.md`） |
| `ARCHIVE_NAME_FORMAT` | `YYYY-MM-DD-<change-name>` | `opsx/archive.md` | 归档目录名格式（日期前缀保证同 capability 多次变更可按时间排序） | 实测 `changes/archive/` 全部条目均为该格式，共 81 条 |
| `ARCHIVE_DIR_NAME` | `archive` | `opsx/archive.md` | 归档子目录名，需 `mkdir -p` 后再 `mv` | 目标已存在时必须报错终止，不允许覆盖 |

### 必须包含的协议字段（此处指 CLI JSON 字段契约）

| 命令 | 字段 | 说明 |
|------|------|------|
| `openspec status --change <name> --json` | `schemaName` | 当前 change 使用的 workflow schema，用于校验"是否本仓库默认 schema" |
| 同上 | `applyRequires` | 实现前置工件 id 数组（spec-driven 下即 `["tasks"]`），**判断可否实现的唯一依据** |
| 同上 | `artifacts[].status` | 取值含 `done` / `ready` / `blocked`，驱动 propose 的生成顺序 |
| 同上 | `isComplete` | 全部工件完成的布尔量，update / archive 用 |
| 同上 | `planningHome.changesDir`、`changeRoot`、`actionContext` | 归档 `mv` 的源/目标与编辑范围约束，**不得用仓库相对路径替代** |
| `openspec instructions apply --change <name> --json` | `contextFiles`、进度三元组、`state` | apply 的输入；`contextFiles` 是 artifact id → 具体文件路径的映射 |

### 必须实现的流程步骤（不可裁减、不可调序）

| 步骤 | 所在文件 | 说明 |
|------|---------|------|
| 读 `contextFiles` 全部文件后再动手 | `opsx/apply.md` Step 4 | 明确要求把 `contextFiles` 列出的**每一个**路径读完；跳过 = 实现脱离设计 |
| 每个 task 完成后立即勾选 | `opsx/apply.md` Step 6 | `- [ ]` → `- [x]` 必须即时更新，否则中断后重入会重复实现 |
| 归档前评估 delta spec 同步状态 | `opsx/archive.md` Step 4 | 用 `artifactPaths.specs.existingOutputPaths` 判断；无 delta spec 则直接归档 |
| 归档目标存在性检查 | `opsx/archive.md` Step 5 | 目标已存在 → `Archive Failed`，给三个可选处置，**不得覆盖** |

### 设计决策（存在多种可行方案时）

| 决策点 | 选定方案 | 备选方案 | 选定理由 |
|--------|---------|---------|---------|
| change 选择粒度 | 未给名字时：上下文推断 → 唯一活跃 change 自动选 → 否则**必须**弹 AskUserQuestion | 直接选最近修改的一个 | 归档/sync 属于不可逆操作，猜错会动到别人的 change（来源: `.claude/commands/opsx/archive.md` Step 1 "Do NOT guess or auto-select"） |
| 流程刚性 | "actions on a change" 流体模型，命令可任意时刻交错调用 | 阶段锁定（paraphrase：proposal→design→tasks→apply 不可回流） | apply 中途若发现设计问题，可直接建议改工件而不是硬走完（来源: `.claude/commands/opsx/apply.md` "Fluid Workflow Integration"） |
| 归档遇警告的处置 | 只警告 + 让人确认，继续归档 | 阻断归档直到工件/任务齐全 | 归档是人的决定，工具不应替人兜底；但必须把警告写进输出模板（来源: `.claude/commands/opsx/archive.md` "Don't block archive on warnings"） |
| explore 是否允许落盘 | 允许创建 OpenSpec 工件，禁止写实现代码 | 完全只读 | 思考需要落点（proposal/design/spec），但"实现"是另一条命令的职责（来源: `.claude/commands/opsx/explore.md` Guardrails） |

## 典型调用链

### 立项（propose）
```
开发者：/opsx:propose add-auth
  → .claude/commands/opsx/propose.md Step 2: openspec new change "add-auth"   ← 建脚手架（含 .openspec.yaml）
  → Step 3: openspec status --change "add-auth" --json                    ← 取 applyRequires / artifacts
  → Step 4: openspec instructions <artifact-id> --change "add-auth" --json ← 取 template/context/rules
      → 写 resolvedOutputPath（proposal.md → specs/** → design.md → tasks.md）
  → Step 5: openspec status --change "add-auth"                           ← 输出收口，提示 /opsx:apply
```

### 实现（apply）与归档（archive）
```
开发者：/opsx:apply add-auth
  → openspec status --change "add-auth" --json          ← schemaName / planningHome / changeRoot / actionContext
  → openspec instructions apply --change "add-auth" --json
      → state=blocked   → 提示 /opsx:continue，停止
      → state=all_done  → 建议 /opsx:archive，停止
      → 否则 读 contextFiles 全部文件 → 逐 task 改代码 → tasks.md 勾 - [x]
  → 输出 "Implementation Complete N/M" 或 "Implementation Paused"（附选项等人工决断）

开发者：/opsx:archive add-auth
  → openspec list --json                       ← 列活跃 change，人工选定
  → openspec status --change "add-auth" --json ← 工件 done 检查 + artifactPaths
  → 读 tasks.md 统计 - [ ] / - [x]             ← 未完成只警告
  → artifactPaths.specs.existingOutputPaths 有 delta → 对比 openspec/specs/<capability>/spec.md
      → 用户选 sync → Task 工具 → Skill: openspec-sync-specs   ← 跨模块：.claude/skills
  → mkdir -p "<planningHome.changesDir>/archive"
  → mv "<changeRoot>" ".../archive/YYYY-MM-DD-add-auth"        ← 目标存在则 Archive Failed
```

## 附：仓库内置文档 / OpenSpec 摘要

- `openspec/specs/change-roadmap/spec.md` 规定：**每个 change 必须独立立项、独立实现与验证**，且立项下游 change 时其依赖的前置 change 必须已具备规格与设计，"不跳过依赖直接实现下游 change"；每个 change 必须有明确范围边界，"某 change 的任务试图实现属于另一 change 范围的能力时，该能力 SHALL 被移出当前 change"（来源: `openspec/specs/change-roadmap/spec.md`）。→ 直接约束 `/opsx:propose` 的范围声明与 `/opsx:update` 的 coherence 检查。
- `openspec/specs/repo-hygiene/spec.md` 规定：README 的"项目结构"小节只允许列出真实存在的目录/文件，且"规格与设计文档的权威来源为 `openspec/`"（来源: `openspec/specs/repo-hygiene/spec.md`）。→ 归档后若结构调整，需同步 README；本知识库的模块文档不得取代 `openspec/` 的权威地位。
- `openspec/config.yaml` 当前 `schema: spec-driven`，且 `context` 与 `rules` 两段为注释占位、**未启用**（来源: `openspec/config.yaml`）。→ `/opsx:propose` 的"不得把 `context`/`rules` 复制进工件"约束在本仓库虽无实际内容，但文本必须保留，否则启用后立即产生污染。
