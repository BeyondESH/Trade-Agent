## 业务意图（这个子模块解决什么问题）

`/opsx:propose` 一次成型的工件，在实现过程中几乎一定会偏。如果放任 Agent"顺手"改工件，就会出现 proposal 说 A、design 说 B、tasks 勾了 C 的三方矛盾，归档时把矛盾一起固化进 `openspec/specs/`。
本子模块的两条命令就是为解决这件事：`update.md` 负责**在既有工件内部重建一致性**（读一处、改一处、再反向检查所有既有工件），`sync.md` 负责**把 delta spec 的意图智能合并进主规格**（`openspec/specs/<capability>/spec.md`，本仓库已有 131 个 capability），且明确要求操作**幂等**（跑两次结果相同）。

两者共同的服务对象是"主规格"这一份长期资产：归档 81 份 change 之后，主规格是唯一还能被后来者读到的真相；因此本子模块的核心风险不是功能缺失，而是**静默丢内容**。

## 对外接口

| 命令 | 方向 | 关键入参 | 业务说明 | 入口文件 |
|------|------|---------|---------|---------|
| `/opsx:update` | 人 → Agent | change 名（可省，模糊时必须弹框，列最近修改的 3–4 个并标 Recommended）+ 修订诉求，或空（= coherence review） | 只修订**已存在**的规划工件并保证互相一致；不创建新工件、不写代码 | `opsx/update.md` |
| `/opsx:sync` | 人 → Agent | change 名（可省，模糊时必须弹框，且只列**含 delta spec** 的 change） | 把 `artifactPaths.specs.existingOutputPaths` 里的 delta spec 逐条合并进主 spec | `opsx/sync.md` |

`/opsx:sync` 是**agent-driven** 操作：CLI 不做机械合并，由 Agent 读 delta + 读主 spec 后直接编辑——这是为了支持"只补一个 scenario、不复制整条 requirement"的局部合并（来源: `.claude/commands/opsx/sync.md` 首段）。

## 实现约束清单

> 这两条命令的约束几乎全是"禁止"类：它们的破坏方式是**静默丢内容**，不会报错。

### 必须定义的常量/枚举

| 标识符 | 值 | 所在文件 | 说明 | 约束由来 |
|-------|----|---------|------|---------|
| `DELTA_SECTION_ADDED` 等四节 | `## ADDED / MODIFIED / REMOVED / RENAMED Requirements` | `opsx/sync.md` | delta spec 的四种意图；解析时必须四类全覆盖 | 漏一类 = 该类需求被静默忽略（来源: `.claude/commands/opsx/sync.md` Step 3） |
| `RENAME_FORMAT` | `FROM:` / `TO:` 成对 | `opsx/sync.md` | RENAMED 的书写格式，找不到 FROM 就不能改名 | 改名靠文本匹配，格式不符会静默失败 |
| `SPEC_PURPOSE_TBD` | `TBD` | `opsx/sync.md` | 新建主 spec 时 Purpose 可写 `TBD` 占位 | 已有大量主 spec 的 Purpose 仍为 `TBD`（如 `openspec/specs/change-roadmap/spec.md`），保留该约定以兼容 |
| `HINT_FRESH_START` | `/opsx:new` | `opsx/update.md` | 当请求改变的是**意图**而非细化时，建议重开 change | 防止把"另起一个需求"伪装成 coherence 修订 |

### 必须包含的协议字段（CLI JSON → 编辑目标映射）

| 命令 | 字段 | 说明 |
|------|------|------|
| `openspec status --change <name> --json` | `artifactPaths.<id>.existingOutputPaths` | **唯一允许编辑的文件清单**（glob 工件已被展开为具体文件，如 `specs/**/*.md`） |
| 同上 | `artifactPaths.<id>.resolvedOutputPath` | **禁止写入**：对 glob 工件它仍是 `specs/**/*.md` 这样的通配模式，写它等于凭空造文件 |
| 同上 | `artifacts[].status`、`isComplete` | update 判断"哪些工件已存在"、`/opsx:continue` 缺口提示的依据 |
| `openspec instructions <artifact-id> --change <name> --json` | `rules`、`template` | 需要大改写时先取该工件的规则与模板再动笔 |

### 必须实现的流程步骤

| 步骤 | 所在文件 | 说明 |
|------|---------|------|
| 双向一致性检查 | `opsx/update.md` Step 4 | 改完目标工件后，须**反向**检查其他既有工件；"an edit to a later artifact may require revising an earlier one"，构建顺序只是阅读顺序，不是修订许可边界 |
| 逐条确认后写入 | `opsx/update.md` Step 5 | 每个修订先展示 + 说明理由，用户确认后才落盘；被否决的修订保持文件不变 |
| 只提示不越权 | `opsx/update.md` Step 6 | 缺工件 → 指向 `/opsx:continue`；已实现但计划改动 → 指向 `/opsx:apply`；全完成 → 指向 `/opsx:archive`。**guidance only - NEVER act on it** |
| 合并时保留未提及内容 | `opsx/sync.md` Step 4c | MODIFIED 只应用 delta 提到的部分，"Preserve scenarios/content not mentioned in the delta" |
| ADDED 撞名视为隐式 MODIFIED | `opsx/sync.md` Step 4c | 目标 requirement 已存在时改为对齐更新，而不是并列插入重复条目 |
| 幂等性 | `opsx/sync.md` Guardrails | 同一 delta 跑两次结果必须一致（第二次应无可改） |

### 设计决策（存在多种可行方案时）

| 决策点 | 选定方案 | 备选方案 | 选定理由 |
|--------|---------|---------|---------|
| 合并执行方 | Agent 智能合并（本命令） | CLI 程序化整节替换 | 需要"只补 scenario 不复制已有内容"；delta 表达的是 *intent*，不是整体替换（来源: `.claude/commands/opsx/sync.md` "Key Principle: Intelligent Merging"） |
| update 的写范围 | 仅 `existingOutputPaths` 里的既有文件 | 允许顺手补齐缺失工件 | 补齐缺失是 `/opsx:continue` 的职责；混在一起会让"修订"变成"扩张范围"（来源: `.claude/commands/opsx/update.md` 第 80 行 "Do not advance the build frontier"） |
| 工件 id / 路径来源 | 一律读 CLI 输出的 `artifact id` 与路径 | 按 spec-driven schema 硬编码 proposal/design/tasks | 自定义 schema 必须零改动可用（来源: `.claude/commands/opsx/update.md` 第 41 行） |
| 意图变更的处置 | 建议 `/opsx:new` 重开 | 在原 change 里大刀阔斧改 | update 的定位是"keep them coherent"，重写意图会破坏已归档/已实现的对应关系 |
| 主 spec 不存在时 | 新建 `openspec/specs/<capability>/spec.md`（Purpose 可 `TBD`，Requirements 放 ADDED） | 拒绝同步并要求先手工建 | 新 capability 是常态（仓库已有 131 个 capability 目录，多数由归档时首次创建） |

## 典型调用链

### 修订既有计划（update）
```
开发者：/opsx:update add-auth（只说 "update"，未给具体诉求）
  → openspec list --json                          ← 取活跃 change + lastModified，人工选最近修改的一个
  → openspec status --change "add-auth" --json    ← artifacts[].status / isComplete
      → 读 existingOutputPaths 全部既有工件（不改 resolvedOutputPath）
      → 判定为 coherence review：逐工件交叉检查矛盾/缺口/重复
      → 逐条展示修订 + 理由，人工确认（否决则文件不动）   ← 禁区：不创建不存在的新工件
      → 大改写前：openspec instructions <artifact-id> --change "add-auth" --json 取 rules/template
  → 输出：已修订工件 / 被否决修订 / 延后给 /opsx:continue 的事项 / 下一步命令
```

### 同步 delta spec 到主规格（sync）
```
开发者：/opsx:sync add-auth
  → openspec list --json                          ← 只列含 specs/ 的 change，人工选定
  → openspec status --change "add-auth" --json    ← artifactPaths.specs.existingOutputPaths = delta 文件清单
  → 对每个 delta：
      读 delta（ADDED/MODIFIED/REMOVED/RENAMED 四节）
      → 读主规格 openspec/specs/<capability>/spec.md（可能不存在）   ← 跨模块：openspec/ 外部知识源
        → ADDED：不存在则新增；已存在则按隐式 MODIFIED 对齐
        → MODIFIED：只改 delta 提到的 scenario/描述，**保留未提及内容**
        → REMOVED：整块删除 requirement
        → RENAMED：按 FROM→TO 文本改名
        → 主规格不存在 → 新建（Purpose 写 TBD + ADDED requirements）
  → 输出摘要（哪些 capability 改了什么）；change 保持活跃，等实现完成后 /opsx:archive
```

## 附：OpenSpec 摘要

- 主规格的物理形态为 `openspec/specs/<capability>/spec.md`，结构固定为 `# <capability> Specification` + `## Purpose` + `## Requirements`，每条 `### Requirement: <名>` 下挂 `#### Scenario:`，scenario 用 `- **WHEN** … - **THEN** … - **AND** …` 断言（来源: `openspec/specs/change-roadmap/spec.md`）。→ `/opsx:sync` 合并时必须保持该四层标题结构，否则后续 `openspec validate` 与 RAG 检索都会失效。
- 归档时新建的 capability 其 Purpose 允许保留 `TBD - created by archiving change <name>`（来源: `openspec/specs/change-roadmap/spec.md` 首行）。→ 与本命令 `SPEC_PURPOSE_TBD` 常量一致，不要"顺手补写 Purpose"造成与其他 capability 不一致。
- 需求粒度约束：本仓库的 requirement 写明"每个 change MUST 独立立项、独立实现与验证"，且"不属于本 change 的能力 SHALL 移出"（来源: `openspec/specs/change-roadmap/spec.md`）。→ 在 `/opsx:update` 中若发现 delta 覆盖了另一个 change 的范围，应先拆分而不是合并。
