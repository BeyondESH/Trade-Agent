## 业务意图（这个子模块解决什么问题）

六个命令文本彼此独立（Claude Code 的斜杠命令没有 include 机制，无法共享片段），但它们必须对 `openspec` CLI 保持**逐字一致**的调用约定：同一个 `--store` 规则、同一套 JSON 字段、同一条"路径只许来自 CLI"的红线。
本子模块把这份重复了六遍的契约固化成一处可检索的知识，解决两个现实问题：① 新增/修改一个命令时不知道该抄什么；② 契约漂移后（六份文本里改了五份）没有任何机制会报警——`openspec validate` 也不会检查命令文件。

它也是本模块**唯一的对外契约面**：这些命令不与行情/交易运行时通信，它们对外的全部形状就是"斜杠命令 → openspec CLI → openspec/ 目录"。

## 对外接口

| 接口 | 方向 | 关键字段 | 业务说明 | 入口文件 |
|------|------|---------|---------|---------|
| `openspec list --json` | 命令 → CLI | change 名、`schema`、`lastModified`、任务进度 | 取活跃 change 供人工选择；update 按最近修改排序 | `opsx/update.md`、`archive.md`、`sync.md`、`explore.md` |
| `openspec status --change <name> --json` | 命令 → CLI | `schemaName`、`planningHome`、`changeRoot`、`actionContext`、`artifacts[]`、`artifactPaths`、`applyRequires`、`isComplete` | 唯一的路径与状态权威源（六命令共用） | 六个命令文件 |
| `openspec instructions <artifact-id> --change <name> --json` | 命令 → CLI | `context`、`rules`、`template`、`instruction`、`resolvedOutputPath`、`dependencies` | 取工件模板与约束；`context`/`rules` 是**给 Agent 的约束，不许写进产物** | `opsx/propose.md`、`update.md` |
| `openspec instructions apply --change <name> --json` | 命令 → CLI | `contextFiles`、进度三元组、`state` | apply 的实现输入与状态机 | `opsx/apply.md` |
| `openspec new change "<name>"` | 命令 → CLI | change 名（kebab-case） | 建脚手架（自动生成 `.openspec.yaml`，实测 81 份归档均含该文件） | `opsx/propose.md` |
| `openspec store list --json` | 命令 → CLI | 注册的 store id | 多 store 环境下的定位入口 | 六个命令的 `Store selection` 段 |

## 实现约束清单

> 契约类约束全部以"六份文件共享文本"的形式存在——改一处就必须改六处，这是本子模块最大的变更风险源。

### 必须定义的常量/枚举

| 标识符 | 值 | 所在文件 | 说明 | 约束由来 |
|-------|----|---------|------|---------|
| `TOOL_ALLOWLIST` | `Bash(openspec:*)` | 六文件 frontmatter `allowed-tools` | 命令只能调 openspec CLI，不得顺手 `mv`/`rm` 仓库其他内容 | 归档所需的 `mkdir`/`mv` 也在命令文本内描述，工具白名单是权限边界 |
| `STORE_FLAG` | `--store <id>` | 六文件 `Store selection` 段 | 多 store 环境下的写入目标选择 | 无 store 时命令作用于最近的本地 `openspec/` 根（本仓库即此情形） |
| `STORE_FLAG_COMMANDS` | `new change / status / instructions / list / show / validate / archive / doctor / context` | 六文件 `Store selection` 段 | **只有**这 9 类命令接受 `--store`；"Other commands do not take the flag" | 来源: `.claude/commands/opsx/update.md` 第 11 行（workspace `anti_patterns` 已登记） |
| `NON_STORE_COMMANDS` | 其余子命令 | 同上 | 给不接受该标志的命令加 `--store` 会直接报错 | CLI 会打印 hints 自动携带该标志，后续跟进命令须保留（"keep it on follow-ups"） |
| `STATUS_FIELD_ARTIFACT_PATHS` | `artifactPaths.<id>.existingOutputPaths` | `update.md`、`sync.md`、`archive.md` | 具体化到磁盘上真实存在的文件（glob 已展开） | 与 `resolvedOutputPath` 是**写 / 禁写**的对立关系，见下 |

### 必须包含的协议字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `schemaName` | string | 该 change 使用的 workflow（本仓库为 `spec-driven`）；命令不得假设工件 id |
| `applyRequires` | array | 实现所需工件 id 列表，判断"能不能开始写代码"的**唯一**依据 |
| `artifacts[].status` | enum | `done` / `ready` / `blocked`；驱动生成顺序与缺口提示 |
| `artifactPaths.<id>.existingOutputPaths` | array | 允许编辑的既有文件；glob 工件已展开 |
| `artifactPaths.<id>.resolvedOutputPath` | string | **禁止写入**：glob 工件下它仍是模式串，写它等于凭空造文件 |
| `planningHome.changesDir` / `changeRoot` | string | 归档的源与目标根目录；不得用 `openspec/changes/<name>` 这类硬编码相对路径替代 |
| `actionContext` | object | 编辑范围约束（planning scope） |
| `contextFiles` | map | apply 时的 artifact id → 具体文件路径；**不得假设文件名**（"don't assume specific file names"） |
| `state` | enum | apply 的 `blocked` / `all_done` / 其他三态分流 |
| 工件 instruction 的 `context`、`rules` | string | **约束而非内容**：`Do NOT copy <context>, <rules>, <project_context> blocks into the artifact` |

### 必须实现的函数/流程（此处指调用序）

| 步骤 | 所在文件 | 说明 |
|------|---------|------|
| 先 `list` 后 `status` | archive / sync / update | 选择即输入；未选定 change 前不得读工件 |
| 先 `status` 后 `instructions` | propose / apply / update | 工件 id 与路径必须来自 `status`，`instructions` 才拿得到模板 |
| 写后复检 | `opsx/propose.md` Step 4b | 每建一个工件都重新 `status`，检查 `applyRequires` 是否全部 `done` 再停 |
| 写前校验存在性 | `opsx/propose.md` 与 `update.md` | 工件文件写完必须 verify 其存在；update 则必须先确认文件在 `existingOutputPaths` 内 |

### 存档字段索引（不可裁减）

| 宏名/字段名 | 值 | 说明 |
|------------|----|------|
| `.openspec.yaml` | 每个 change 目录内（归档后随目录移动） | change 元数据；`schema` + `created` 两字段（如 `schema: spec-driven` / `created: 2026-07-26`） |
| `archive/` 目录名 | `archive` | 归档区的固定子目录名；`planningHome.changesDir/archive/` |
| change 目录名 | kebab-case | `propose` 从需求描述派生（"add user authentication" → `add-user-auth`） |

> ⚠️ `.openspec.yaml` 必须随 change 目录一起移动，不得在归档时剥离——`archive.md` 明确写 "Preserve .openspec.yaml when moving to archive"。

### 设计决策（存在多种可行方案时）

| 决策点 | 选定方案 | 备选方案 | 选定理由 |
|--------|---------|---------|---------|
| 契约的载体 | 在六个命令文件里**各复制一段**同构文本 | 抽一个共享 include / 引用文档 | Claude Code 斜杠命令无 include 机制；`.claude/skills` 与 `.opencode/commands` 也各有副本，只能靠文本一致 |
| 路径来源 | 一律取 `planningHome` / `changeRoot` / `artifactPaths` | 直接拼 `openspec/changes/<name>` | 支持 store（独立 OpenSpec 仓库）与自定义 planningHome；硬编码路径在多 store 下会写错目录 |
| 命令命名分隔符 | `/opsx:<cmd>`（Claude Code） | `/opsx-<cmd>`（OpenCode） | 宿主语法差异；两套文件内容其余部分必须保持一致 |
| change 自动选择 | 仅唯一活跃 change 时自动选，其余弹框 | 按 lastModified 自动选 | 见 `workflow` 子文档；归档/sync 不可逆 |

## 典型调用链

### 共享契约：一次完整的 status → instructions 往返
```
任意 /opsx:* 命令
  → Bash: openspec status --change "<name>" --json        ← schemaName / artifacts / artifactPaths / applyRequires
      → 若需要模板或实现输入：
        Bash: openspec instructions [apply] --change "<name>" --json
            ← context/rules（约束，不入产物）/ template / contextFiles / state
      → 路径解析：planningHome.changesDir + changeRoot（归档案） / existingOutputPaths（编辑案）
      → 写操作后回到 status 复检                                    ← 六命令共同收口方式
```

### 多 store 分流
```
命令启动（任意 opsx 命令）
  → 用户是否指定 store / 工作是否在某 store 中？
      是 → Bash: openspec store list --json  → 取 id
           → 仅在 new change/status/instructions/list/show/validate/archive/doctor/context 上加 --store <id>
           → CLI 打印的 hints 已带该标志 → 后续命令保留                                  ← 禁止给其他子命令添加
      否 → 作用于最近的本地 openspec/ 根（本仓库即为该情形）
```

## 附：OpenSpec 摘要

- `openspec/config.yaml` 目前仅声明 `schema: spec-driven`；`context` 与 `rules` 段落**全部是注释占位、未启用**（来源: `openspec/config.yaml`）。→ CLI 的 `instructions` 输出中 `context`/`rules` 可能为空，命令文本的"不要复制进工件"约束在本仓库暂无实际触发，但必须保留以兼容启用后的行为。
- 每个 change 目录内固定存在 `.openspec.yaml`（字段 `schema` + `created`，如 `schema: spec-driven` / `created: 2026-07-26`），归档后随目录迁移（来源: `openspec/changes/archive/2026-07-26-ai-agent-core/.openspec.yaml`、`.../2026-08-20-fix-kline-history-gap/.openspec.yaml`）。→ 对应 `changeRoot` 的定义与归档"不得剥离该文件"的约束。
- delta spec 位于 change 内的 `specs/<capability>/spec.md`，其归宿是主规格 `openspec/specs/<capability>/spec.md`（来源: `openspec/changes/archive/2026-08-20-fix-kline-history-gap/specs/`、`openspec/specs/`）。→ 印证 `artifactPaths.specs.existingOutputPaths` 会展开出多个 capability 级路径。
