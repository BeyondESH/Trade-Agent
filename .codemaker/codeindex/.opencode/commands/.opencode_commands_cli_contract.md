## 典型调用链

### 公共前缀（每条命令都走）

```
用户输入 /opsx-<verb> [arg] → 宿主按 .opencode/commands/<verb>.md 加载提示词
  → Store selection 段（若用户点名 store）
      → openspec store list --json 取 id
      → 后续每次读写规格/change 的调用一律追加 --store <id>          ← 白名单外的子命令不接受该标志
  → openspec list --json（需要选 change 时）→ AskUserQuestion 选择框 →  announce "Using change: <name>"
  → openspec status --change "<name>" --json                            ← 本模块的"读真值"入口
      → 一切路径（changeRoot / planningHome.changesDir / artifactPaths.*）只从这份 JSON 取
  → 分支到具体命令（见 workflow / artifacts 子文档的调用链）
```

### 版本漂移探测（维护者用）

```
diff .opencode/commands/opsx-<verb>.md .claude/commands/opsx/<verb>.md   ← 应只差命令名分隔符 + Claude 侧 frontmatter
diff .opencode/commands/opsx-<verb>.md .opencode/skills/<openspec-*>/SKILL.md  ← 当前差异 16~148 行，archive/explore 最重
```

## 实现约束清单

> 任何对"CLI 调用方式 / 宿主适配段"的改动都要过以下核对。

### 必须遵守的契约

| 标识符 | 值 | 所在文件 | 说明 | 约束由来 |
|-------|----|---------|------|---------|
| `CLI_SCHEMA` | `spec-driven` | `openspec/config.yaml` | 全仓 change 统一 schema；自定义 schema 必须在**不改本模块文本**的前提下可用 | `opsx-update.md` L37 明文要求（`anti_patterns: do_not`） |
| `STORE_COMMAND_WHITELIST` | `new change / status / instructions / list / show / validate / archive / doctor / context` | 6 份 Store selection 段 | `--store <id>` 只加在这九个上；命令打印的 hint 已自带该标志，续跑时要保留；无 store 时作用于最近的本地 `openspec/` 根 | 段首逐字重复 6 次，任一处改写即产生宿主间分歧 |
| `FIELD_INSTRUCTION_KEYS` | context / rules 属"给你的约束" | `opsx-propose.md` L58-59、L66、L98 | 严禁把 `<context>` `<rules>` `<project_context>` 抄进工件 | 保证工件在任何 schema/项目下都可移植 |
| `FIELD_ARTIFACT_PATHS` | glob 工件的 `resolvedOutputPath` 是模式串 | `opsx-update.md` L39 | 写盘只允许用 `existingOutputPaths`（见 artifacts 子文档） | 否则会写出名为 `**` 的文件 |
| `COMMAND_NAME_SCHEME` | 连字符 `/opsx-<verb>` | OpenCode 全目录 | OpenCode 不做 `group/action` 命名空间；Claude 版才是 `/opsx:<verb>` | 唯一稳定的跨宿主文本差异，改写会破坏其中一侧的调用 |
| `HOST_TOOL_NAMES` | 9 处 | propose/apply/archive/sync/update | `AskUserQuestion`(6) / `TodoWrite`(1) / `Task + subagent_type: "general-purpose"`+`Skill tool`(2) 均为 Claude Code 工具名 | OpenCode 侧不保证同名工具，须复核实际行为 |

### 禁止事项（含后果）

| 禁忌 | 后果 | 出处 |
|------|------|------|
| 硬编码 `openspec/changes/<name>/...` 作为读写路径 | store 模式下 OpenSpec 根在别处，写动作会落到错误仓库；本地规划主目录（planningHome）一旦变更即全部失效 | Store selection 段 + `status --json` 的 `planningHome/changeRoot/actionContext` |
| 在命令里假设 tasks 一定在 `tasks.md`、规格一定在 `specs/<capability>/spec.md` | 换 schema 后 apply 找不到任务清单、sync 找不到 delta | `opsx-apply.md` L145、`opsx-update.md` L37 |
| 把 `--store` 加到白名单外的子命令 | CLI 直接报未知选项，用户被无信息错误卡住 | Store selection 段（"Other commands do not take the flag"） |
| 只改 4 份拷贝中的 1 份 | 同一需求在 OpenCode 与 Claude Code 下表现不同；`workspace.json.anti_patterns` 会继续把未同步副本当约束喂给代理 | 本模块 72 条 `do_not` 与 `.claude/*` 采集条目同源 |
| 把项目级撰写规范写进命令正文（而不是 `openspec/config.yaml` 的 `rules`） | 规范与流程耦合，schema 升级或换项目时命令文本需重写，且对 Claude 侧不生效 | `openspec/config.yaml` 的 rules 注释示例 |
| 在宿主工具不可用时静默降级为"自己拍脑袋继续" | 本该由人确认的取参/归档决策被自动替代，等于绕过命令的核心安全阀；应显式说明并停下来问 | `opsx-archive.md` L20、`opsx-apply.md` L144 |

### 设计决策

| 决策点 | 选定方案 | 备选方案 | 选定理由 |
|--------|---------|---------|---------|
| 状态来源 | `openspec status --json` | 自行扫 `openspec/changes/**` 目录判断 | CLI 才有 schema 语义（ready/blocked/done 与依赖图），手扫会得到错误的推进顺序 |
| 提示词载体 | `.opencode/commands/*.md`（人触发）+ `.opencode/skills/*`（代理自选）双份 | 只留命令版 | OpenCode 的 skill 与 command 解析路径不同，去掉任一都会让另一条入口失效；两份文本必须同调 |
| 跨宿主差异最小化 | 只允许命令名分隔符 + frontmatter 两处不同 | 各自按宿主习惯重写正文 | 差异越小，`diff` 越能当回归测试用；上面"版本漂移探测"链路依赖这一约定 |
| OpenCode 版 frontmatter | 仅 `description`（宿主展示用） | 保留 Claude 的 `name/allowed-tools/category/tags` | opencode 命令 frontmatter 无 `allowed-tools` 权限模型，工具白名单改由宿主全局配置；因此 `Bash(openspec:*)` 这层"只准跑 openspec"的软约束在 OpenCode 侧**并不生效**，写码权限的实际闸门是流程文本 |

## 附：OpenSpec 摘要

> 📋 本节内容来源于 OpenSpec：`openspec/config.yaml`、`openspec/changes/archive/2026-07-26-market-data-foundation/.openspec.yaml`、`openspec/changes/`、`openspec/specs/`（仅提炼接口契约，非完整转录）

- `openspec/config.yaml` 只有 `schema: spec-driven` 一行生效，`context` 与 `rules` 两段仍为注释模板；即当前六条命令从 `openspec instructions` 拿到的项目级定制注入为空，工件结构完全来自内置 schema 模板。要给代理加"提案不超 500 词 / 必含 Non-goals / 任务按 2 小时粒度"这类规则，正确落点是该文件而非本模块。（来源: openspec/config.yaml）
- 每个 change 目录自带 `.openspec.yaml`，内容为 `schema: spec-driven` + `created: <日期>`，被归档的 change 同样保留该文件——这印证了 `/opsx-archive` 中"`.openspec.yaml` 随目录一起 `mv`"的守卫条件。（来源: openspec/changes/archive/2026-07-26-market-data-foundation/.openspec.yaml）
- 现网 `openspec/changes/` 下活跃 change 为 0、`changes/archive/` 有 81 条、`specs/` 有 131 个 capability；`openspec list --json` 实测返回 `{"changes": [], "root": {"path": "D:\\work\\project\\trade", "source": "nearest"}}`，即本仓库走"本地最近 openspec 根"而非 store 模式，`--store` 分支在默认工作流下永远不触发——不要为它删掉其他分支的前置检查。（来源: openspec/changes/、openspec/specs/）
- CLI 侧与主规格相关的既有能力：`openspec archive <change> [--yes] [--skip-specs] [--no-validate] [--json]`（归档并更新主规格）、`openspec validate [--all|--changes|--specs] [--strict] [--json]`、`openspec doctor`、`openspec context`、`openspec schemas`。本模块选择让 agent 承担 sync 而非直接调 CLI（取舍见 artifacts 子文档设计决策表）。（来源: openspec CLI 帮助文本；仓库内 openspec 工件约定）
