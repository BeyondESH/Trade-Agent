## 对外接口（命令契约，单行格式便于检索）

| 接口 | 方向 | 关键输入 | 业务说明 | 入口 |
|------|------|---------|---------|------|
| `/opsx-explore [主题]` | 人 → 代理 | 任意自然语言（想法/问题/change 名/对比），可为空 | 思考伙伴：读码、画图、比方案；**禁止实现**；可应要求创建 OpenSpec 工件 | `opsx-explore.md` |
| `/opsx-propose [name]\|[描述]` | 人 → 代理 → CLI 写盘 | kebab-case change 名，或一段描述（由代理推导名字） | 一条命令产出 change 全套工件直到 apply-ready；完成后引导 `/opsx-apply` | `opsx-propose.md` |
| `/opsx-apply [name]` | 人 → 代理 → 改代码 + 回写 tasks | change 名；缺省可推断/唯一可自动选，含糊必须问 | 逐条实现 tasks 并勾选；支持任意时点插入（非阶段锁定） | `opsx-apply.md` |
| `/opsx-archive [name]` | 人 → 代理 → 写 openspec/changes/archive | change 名；缺省**只能**由人选 | 校验工件与 tasks → 评估 delta 同步 → `mv` 归档 → 输出摘要 | `opsx-archive.md` |

## 典型调用链

### 立项（propose）

```
/opsx-propose <描述> → opsx-propose.md Step1 取参（AskUserQuestion 开放输入）
  → openspec new change "<name>"                       ← 建目录 + .openspec.yaml
  → openspec status --change "<name>" --json           ← applyRequires / artifacts / planningHome / changeRoot / artifactPaths / actionContext
  → 循环：openspec instructions <artifact-id> --change "<name>" --json
      → 读 dependencies 已完成工件 → 按 template 写 resolvedOutputPath   ← 本模块写盘点
  → openspec status --change "<name>"                  ← 复检直到 applyRequires 全 done
  → 输出：change 名与位置 + 工件清单 + 提示跑 /opsx-apply
```

### 实现（apply）

```
/opsx-apply [name] → 选定 change（推断/唯一自动选/否则 list --json + 选择框）
  → openspec status --change "<name>" --json           ← schemaName + 承载 tasks 的工件
  → openspec instructions apply --change "<name>" --json ← contextFiles / progress / task list / state
  → state=blocked → 提示补齐工件（正文指向 /opsx-continue，实际不存在）→ 停止
  → 读 contextFiles 全部文件 → 逐条实现（改 backend/ 或 frontend/ 代码）  ← 跨界到业务代码的唯一入口
    → tasks 文件 "- [ ]" → "- [x]"（每条即时回写）
  → 输出：N/M tasks complete；全完成则建议 /opsx-archive
```

### 归档（archive）

```
/opsx-archive [name] → list --json + 选择框（只列未归档活跃 change）   ← 禁止自动选
  → openspec status --change "<name>" --json（artifacts 是否全 done）→ 未完成：警告 + 二次确认（不拦截）
  → 读 tasks 计数 "- [ ]" vs "- [x]" → 未完成：警告 + 二次确认；无 tasks 文件则跳过警告
  → artifactPaths.specs.existingOutputPaths 有 delta？→ 逐条与 openspec/specs/<capability>/spec.md 比对并汇总
      → 人选 Sync now → 委派 openspec-sync-specs（subagent）执行主规格合并   ← 跨模块：见 sync 子文档
  → mkdir -p "<planningHome.changesDir>/archive"
  → mv "<changeRoot>" "<planningHome.changesDir>/archive/YYYY-MM-DD-<name>"   ← 本模块终点，目标已存在则报错
```

## 实现约束清单

> 改动这四条命令（或其镜像拷贝）前必须逐条核对。

### 必须遵守的流程常量/枚举

| 标识符 | 值 | 所在文件 | 说明 | 约束由来 |
|-------|----|---------|------|---------|
| `PROPOSE_ARTIFACT_TRIPLE` | proposal / design / tasks | `opsx-propose.md` | 一次产出的三件套；实际工件以 schema 的 `applyRequires` 为准，不得只写三份 | 现网 81 个归档 change 一律含这三件 + `specs/**`（来源: openspec/changes/archive/2026-07-26-market-data-foundation/） |
| `CHANGE_FILE_KEEP_ON_MOVE` | `.openspec.yaml` 含 `schema` + `created` | `opsx-archive.md` | 归档时随目录整体移动，禁止剔除或重写 | 每个归档目录都保留该文件（来源: openspec/changes/archive/2026-07-26-market-data-foundation/.openspec.yaml） |
| `ARCHIVE_DIR_NAME_FORMAT` | `YYYY-MM-DD-<change-name>` | `opsx-archive.md` | 归档名必须由当前日期 + change 名拼；同日到冲突即失败 | 归档目录实测全部符合此格式（来源: openspec/changes/archive/） |
| `TASK_CHECKBOX_DONE` | `- [x] N.M 描述` | `opsx-apply.md` | 编号分节 + 复选框是唯一可被 archive 计数的格式 | 现网 tasks 均此格式（来源: openspec/changes/archive/2026-07-26-market-data-foundation/tasks.md） |
| `EXPLORE_CAPTURE_TABLE` | 四类洞察 → 四个落点 | `opsx-explore.md` | 思考成果的归置规范：需求进 spec、决策进 design、范围进 proposal、工作项进 tasks | 与 `spec-driven` schema 的工件职责一致（来源: openspec/config.yaml） |

### 禁止事项（含后果）

| 禁忌 | 后果 | 出处 |
|------|------|------|
| explore 模式写实现代码（创建 OpenSpec 工件不算实现） | 需求未经 proposal/design 约束即落地，事后无人能追溯为什么这么做 | `opsx-explore.md` L13、L164（`anti_patterns: do_not`） |
| explore 中"自动帮用户把洞察写进工件" | 替用户做了范围决策；必须"提议 + 由人拍板" | `opsx-explore.md` L134、L168 |
| propose 把 CLI 返回的 `context` / `rules` 抄进工件正文 | 规划文档被项目上下文污染，schema 换版即失效 | `opsx-propose.md` L58-59、L66、L98 |
| propose 未确认意图就开工建 change | 生成一套方向错误的工件，后续 apply 会把错误意图实现进代码 | `opsx-propose.md` L29 |
| apply 用硬编码文件名代替 `contextFiles` | 非 `spec-driven` 的自定义 schema 直接找不到工件；spec-driven 恰好也叫 proposal/specs/design/tasks，很容易掩盖问题 | `opsx-apply.md` L145 |
| apply 在任务含糊时自行猜测 | 交易/风控类逻辑猜错即资金口径错误；命令要求"暂停并问" | `opsx-apply.md` L144 |
| apply 一批任务做完再统一勾选 | 中途被打断即丢失进度，archive 的完成度校验失真 | `opsx-apply.md` Step 6 |
| archive 猜测或自动选 change | 归档是不可逆 `mv`，错选会把别人正在做的 change 移出活跃列表 | `opsx-archive.md` L20 |
| archive 因警告而拒绝归档 | 阻塞实验性流程；规范是"告知 + 确认"，不是拦截 | `opsx-archive.md` L153 |
| 新增命令继续引用 `/opsx-continue`、`/opsx-new` | 本目录与 `.claude/commands/opsx` 都没有这两个命令，用户会得到未知命令；要么补齐文件，要么改指向已存在的 `/opsx-propose` | `opsx-apply.md` L44、`opsx-update.md` L49/L61/L69/L76 |

### 设计决策

| 决策点 | 选定方案 | 备选方案 | 选定理由 |
|--------|---------|---------|---------|
| 归档由谁做 | 代理 `mkdir -p` + `mv`，主规格合并交给 `openspec-sync-specs` | 直接调 `openspec archive`（CLI 自身即"归档并更新主规格"） | 代理归档可在 `mv` 前逐条呈现 delta 与主规格的差异并让人选择同步；代价是选 "Archive without syncing" 时主规格永不更新——**这是本模块最需要人工复核的分工** |
| 未完成项处理 | 警告 + 二次确认，允许继续归档 | 硬拦截 | 实验性流程允许 doc-only / artifact-only change 提前归档；仓库确有只改工件不改代码的 change（来源: openspec/changes/archive/2026-09-20-spec-drift-cleanup/design.md） |
| propose 的产物范围 | 只补 `applyRequires` 列出的工件 | 生成 schema 中全部工件 | 保持向前推进的最小成本；缺的工件交给后续动作，不在立项时铺满 |
| 命令文件名与调用名 | `opsx-<verb>.md` → `/opsx-<verb>`（连字符） | 沿用 Claude 的 `opsx/<verb>.md` → `/opsx:<verb>`（冒号命名空间） | OpenCode 的 commands 目录是平铺发现，不支持冒号命名空间；这也是与 `.claude/commands` 唯一稳定的两处差异之一 |

## 附：OpenSpec 摘要

> 📋 本节内容来源于 OpenSpec：`openspec/config.yaml`、`openspec/changes/archive/2026-07-26-market-data-foundation/*`、`openspec/changes/archive/2026-09-20-spec-drift-cleanup/*`、`openspec/specs/repo-hygiene/spec.md`（仅提炼流程契约，非完整转录）

- 仓库根 schema 为 `spec-driven`；`config.yaml` 的 `context` 与 `rules`（按工件粒度，如 `proposal` / `tasks`）正是四条命令通过 `openspec instructions` 消费的项目级注入口。当前仓库这两项均为注释状态未填，因此工件结构完全取决于内置 schema 模板——想让代理稳定遵守某条撰写规范，**唯一正确的做法是填 `openspec/config.yaml` 的 `rules`，而不是改本模块的命令文本**。（来源: openspec/config.yaml）
- 工件内容模板（`propose` 产出、`apply` 读取时必须对齐的形状）：`proposal.md` = `## Why` / `## What Changes` / `## Capabilities`（New / Modified，逐条列 capability 名）/ `## Impact`；`design.md` = `## Context` / `## Goals / Non-Goals` / `## Decisions`（编号 D1…Dn，每条含备选方案与放弃理由）/ `## Risks`；`tasks.md` = `## N. 分节` + `- [x] N.M`。（来源: openspec/changes/archive/2026-07-26-market-data-foundation/proposal.md,design.md,tasks.md）
- 需求即真相原则：当规格与实现冲突时，本仓库以"实现"为准修订规格，并允许出现纯粹的 artifact-only change（只改规划工件、不改应用代码）。（来源: openspec/changes/archive/2026-09-20-spec-drift-cleanup/design.md）
- 仓库级权威性约定：规格与设计文档的权威来源是 `openspec/`，README 的项目结构小节不得与之并列成为第二事实源——这决定了本模块输出的落点选择。（来源: openspec/specs/repo-hygiene/spec.md）
- 现网状态基准：`openspec/changes/` 下活跃 change 数为 0（仅 `archive/` 一层，81 个归档条目），`openspec/specs/` 有 131 个 capability。任何"列举活跃 change"的命令步骤在当前仓库都会得到空集合，命令必须显式提示而不是静默继续。（来源: openspec/changes/, openspec/specs/）
