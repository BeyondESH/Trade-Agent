## 典型调用链

### 修订工件（update）

```
/opsx-update [name] → openspec list --json（按 lastModified 排序）→ 选择框        ← 禁止自动选中
  → openspec status --change "<name>" --json                                        ← status/instructions 契约见 cli_contract
      取 schemaName / artifacts(status: done|ready|blocked) / isComplete
        / artifactPaths.<id>.existingOutputPaths / planningHome / changeRoot / actionContext
  → 读被请求触碰的工件 + 该 change 其余已存在工件 → 双向自洽检查（后改的可反推先改的要修）
  → 逐个工件呈现"拟改内容 + 理由" → 人确认后才写盘                                  ← 本模块唯二写盘点之一
      被拒绝的修订就不写；工件已自洽就明说并零改动
  → 需要大改 → openspec instructions <artifact-id> --change "<name>" --json（先取 rules + template 再写）
  → 输出：改了哪些 / 拒了哪些 / 哪些推给 /opsx-continue / 下一步建议（只建议，不执行）
```

### 同步主规格（sync）

```
/opsx-sync [name] → openspec list --json → 选择框（只列带 specs/ delta 的 change）
  → openspec status --change "<name>" --json → artifactPaths.specs.existingOutputPaths  ← delta 清单来自 CLI，不扫盘
  → 对每个 delta：读 delta + 读 openspec/specs/<capability>/spec.md（可能不存在）
      ADDED    → 主规格无则追加；已有则按 MODIFIED 处理（不得重复堆叠同名 requirement）  ← 幂等关键
      MODIFIED → 定位同名 requirement，只并入 delta 提到的 scenario/描述，其余原样保留
      REMOVED  → 删除整块 requirement
      RENAMED  → 按 FROM:/TO: 改名（常与 REMOVED+ADDED 成对出现）
      主规格不存在 → 新建文件并补 ## Purpose（可 TBD） + ## Requirements
  → 无 delta 时：告知并停止（不得虚构合并）
  → 输出：按 capability 分组的 added/modified/removed/renamed 摘要；change 仍活跃，提示"实现完成后再归档"
```

## 实现约束清单

> 这两条命令是本模块**唯一直接改写主规格**的入口，改动前逐条核对。

### 必须遵守的字段/格式

| 标识符 | 值 | 所在文件 | 说明 | 约束由来 |
|-------|----|---------|------|---------|
| `DELTA_SECTION_*` | ADDED / MODIFIED / REMOVED / RENAMED | `opsx-sync.md` | 四段头是 delta 的解析锚点；缺段即无合并 | 现网归档 delta 均按此四段撰写（来源: openspec/changes/archive/2026-09-20-spec-drift-cleanup/proposal.md） |
| `REQUIREMENT_HEADING_FORMAT` / `SCENARIO_HEADING_FORMAT` | `### Requirement:` / `#### Scenario:` + WHEN/THEN/AND | `opsx-sync.md` | 合并产物必须与主规格既有层级同构，否则 `openspec validate` 不过 | 131 个主规格全部同构（来源: openspec/specs/repo-hygiene/spec.md） |
| `UPDATE_EDIT_WHITELIST` | `existingOutputPaths` | `opsx-update.md` | 只写磁盘上已存在的具体文件（glob 工件已展开） | 保证 update 不推进 build frontier（`anti_patterns: do_not`） |
| `STATUS_ARTIFACT_STATE_ENUM` | done / ready / blocked | `opsx-update.md` | 状态只用于判断"还缺什么"，不用于推导工件名 | 自定义 schema 必须零改动即可工作 |
| `NEW_MAIN_SPEC_SECTIONS` | Purpose + Requirements | `opsx-sync.md` | 新建主规格的最小骨架 | 真实主规格 Purpose 常为 `TBD - created by archiving change <name>. Update Purpose after archive.`（来源: openspec/specs/repo-hygiene/spec.md） |

### 禁止事项（含后果）

| 禁忌 | 后果 | 出处 |
|------|------|------|
| 把 MODIFIED 写成"整节替换"（复制全部既有 scenario 或覆盖整块） | 主规格中未被 delta 提及的 scenario 被静默删除，属不可逆知识损失；同步应当是**局部并入** | `opsx-sync.md` L59、L113（`anti_patterns: do_not`） |
| 合并前先读 delta 却不同步读主规格就编辑 | 无法判断 requirement 是否已存在，重复堆叠同名 requirement，破坏幂等（"跑两次结果应一致"是明文要求） | `opsx-sync.md` Guardrails |
| update 顺手创建缺失工件 | 越过立项阶段，工件在没有 rules/template 约束下生成，方向性错误被固化 | `opsx-update.md` L49、L76 |
| update 在 glob 型工件下写 `resolvedOutputPath` | 写盘写出一个文件名里带 `**` 的垃圾文件，或覆盖整类工件 | `opsx-update.md` L39 |
| update 按硬编码工件名（proposal/tasks/design）分支 | `spec-driven` 之外自定义 schema 立即失效 | `opsx-update.md` L37 |
| update 改实现代码 | 计划与代码由两条不同审批链管理；改了代码等于绕过 `/opsx-apply` 的 tasks 勾选与完成度统计 | `opsx-update.md` L73 |
| update/sync 猜测或自动选 change（update 还要求把最新一项标 Recommended） | 改错 change 的工件无从察觉；工件是多人共享的规划资产 | `opsx-update.md` L25、`opsx-sync.md` L21 |
| update 未逐条向人确认就写盘 | "修订"与"回滚"无法区分；被拒绝的想法会被静默落盘 | `opsx-update.md` L77 |
| 用 `/opsx-new`、`/opsx-continue` 作为常规出口 | 二者在本宿主不存在；意图发生变化时应指向 `/opsx-propose`（等价新建）而非幻影命令 | `opsx-update.md` L78、L61 |

### 设计决策

| 决策点 | 选定方案 | 备选方案 | 选定理由 |
|--------|---------|---------|---------|
| 主规格合并由谁做 | agent 智能合并（`/opsx-sync`） | CLI 机械合并（`openspec archive` 一次性更新主规格） | 支持"只加一个 scenario 而不复制整节"的 partial update，delta 表达的是 intent 而非 wholesale replacement；代价是必须靠流程自觉保证合并发生 |
| ADDED 命中已存在 requirement | 按 MODIFIED 处理（更新以对齐） | 报错中止 / 追加重复块 | 保证幂等：重复运行 sync 不应产生第二份同名 requirement |
| update 的读取范围 | 该 change 全部**已存在**工件（双向自洽，后段可反推前段） | 只改被点名那一份 | 单文件修订会让 proposal 的范围与 design 的决策互相打脸；构建顺序只是阅读顺序，不是修订约束 |
| 意图变化 vs 细化 | 细化 → update；意图变化 → 建议新建（正文写作 `/opsx-new`） | 一律就地改写 | "Update vs. Start Fresh" 启发式：推翻方向的修订会让历史工件与现实不符 |
| 新建主规格的 Purpose | 允许 TBD，后续人工补 | 强制当场写完整 Purpose | 与 CLI `archive` 生成的实际产物一致，避免代理编造目的 |

## 附：OpenSpec 摘要

> 📋 本节内容来源于 OpenSpec：`openspec/specs/repo-hygiene/spec.md`、`openspec/changes/archive/2026-09-20-spec-drift-cleanup/{proposal,design}.md`、`openspec/config.yaml`（仅提炼与合并语义相关的条款，非完整转录）

- 主规格合并的另一条既有路径是 `openspec archive`（CLI 描述即"Archive a completed change and update main specs"，并带 `--skip-specs`（供 tooling/doc-only change）、`--no-validate`、`-y`）。本模块的 sync/archive 选择由 agent 承担合并，因此**任何绕过 `openspec archive` 的手工 `mv` 都必须先完成 sync**，否则主规格永久落后。归档类 change（doc-only）应视为 `--skip-specs` 的等价情形。（来源: openspec/config.yaml 的 schema 约定 + CLI 帮助文本）
- 真实一次清扫的规模说明漂移代价：`spec-drift-cleanup` 一个 change 就要 REMOVED 3 个 capability 的全部 requirement、MODIFIED 多格措辞、并以 REMOVED+ADDED 成对重命名 requirement——若当初 sync/archive 未跑，废弃规格会被后续实现者当作事实重建。（来源: openspec/changes/archive/2026-09-20-spec-drift-cleanup/proposal.md）
- 主规格的 `### Requirement:` 正文使用 `SHALL / MUST / MUST NOT` 规范化措辞，`#### Scenario:` 使用 WHEN/THEN/AND 三段式；sync 产出的 requirement 必须沿用同一措辞风格，否则 `openspec validate --strict` 与人工复核都会失焦。（来源: openspec/specs/repo-hygiene/spec.md）
- 本仓库既有需求以中英混排书写（正文中文、`SHALL/MUST` 关键字英文），`/opsx-update` 的 coherence 修订不得把中文需求主体翻译成英文，也不得反向删掉中文说明。**（来源: openspec/specs/repo-hygiene/spec.md）**
